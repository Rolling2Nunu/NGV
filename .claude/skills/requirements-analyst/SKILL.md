# 요구사항 분석가 (Requirements Analyst)

이 스킬은 자동차 임베디드 소프트웨어/시스템 프로젝트에서 ISO 26262와
A-SPICE PAM 4.1을 준수하는 요구사항 명세서를 작성하기 위한 절차와 규칙을
정의한다.

## 0. 템플릿 우선 원칙

- 사용자가 별도로 제공하는 요구사항 명세서 템플릿이 있으면 **그 템플릿의
  구조/항목/서식을 최우선으로 따른다.** 템플릿은 보통 저장소 내
  `templates/` 디렉터리(예: `templates/requirements-spec-template.*`)에
  위치할 것으로 예상되지만, 정확한 경로는 사용자에게 확인한다.
- 아직 템플릿이 제공되지 않았다면, 이 스킬의 "8. 임시 산출물 구조"를
  사용해 우선 작성하고, **템플릿이 제공되는 즉시 그 구조에 맞게 재정렬**한다.
  이 사실(아직 정식 템플릿이 아니라는 점)을 산출물 상단에 명시한다.
- 템플릿과 아래 규칙(ISO 26262/A-SPICE/ISO 25010/추적성 등)이 충돌하면,
  템플릿의 항목 배치는 따르되 이 스킬이 요구하는 내용(예: 검증방안,
  Input/Output, 추적 ID)이 누락되지 않도록 사용자에게 알리고 템플릿 보완을
  제안한다.

## 1. 저작권 유의

ISO 26262, ISO/IEC 25010, A-SPICE PAM 4.1의 원문(조항 번호, 정확한 문구,
표 전문)은 각각 ISO와 VDA/intacs의 저작물이다. 이 스킬은 공개적으로 널리
알려진 프레임워크 구조(품질특성 8개 분류명, 요구사항 공학의 일반적 품질
속성 명칭 등)만 사용하며, 원문을 통째로 인용하지 않는다. 세부 조문이
필요하면 사용자가 보유한 원본 표준 문서를 참조하도록 안내한다.

## 2. 요구사항 ID 및 분류 체계

- 모든 요구사항에는 고유하고 변경되지 않는 ID를 부여한다.
  예: `REQ-SYS-F-001`(시스템, 기능), `REQ-SYS-NF-001`(시스템, 비기능),
  `REQ-SW-F-001`(소프트웨어, 기능) 등. 프로젝트 템플릿이 지정한 ID 규칙이
  있으면 그것을 우선한다.
- 요구사항은 최소한 다음으로 분류한다: 기능 요구사항(Functional),
  비기능 요구사항(Non-functional), 인터페이스 요구사항(Interface),
  안전 요구사항(Safety, ISO 26262 관련 시).
- ISO 26262 관련 요구사항에는 ASIL 등급(QM, A, B, C, D)과 그 근거(상위
  안전 목표/안전 요구사항으로부터의 할당 근거)를 함께 기재한다. ASIL을
  임의로 지어내지 않으며, 근거 문서(HARA, 안전 목표 등)가 없으면 "ASIL 미정
  — 근거 문서 필요"로 표기한다.

## 3. 기능 요구사항 작성 규칙

각 기능 요구사항은 다음을 포함한다.

1. **ID / 제목 / 우선순위 / 상태(초안·검토중·승인)**
2. **서술문**: "시스템은 <조건>일 때 <행위>를 수행해야 한다(shall)" 형태의
   능동태, 단문. 하나의 요구사항 문장에는 하나의 요구사항만 담는다(원자성).
3. **Input / Output (자연어 선언)**: 하위 설계 문서(SW 아키텍처, 상세설계)가
   그대로 참고할 수 있도록, 이 기능이 받는 입력과 만들어내는 출력을 자연어로
   명확히 선언한다.
   - 예: `Input: 차속 센서로부터의 차량 속도 값(km/h), 운전자의 크루즈 설정
     버튼 입력`
   - 예: `Output: 목표 가속도 명령(m/s^2), 크루즈 상태 표시 신호`
   - 물리량에는 단위를, 이산 신호에는 값의 종류(열거값)를 함께 기재한다.
4. **UML/SysML 다이어그램**: 요구사항의 동작/흐름/상태를 시각적으로 표현할
   필요가 있으면 PlantUML 또는 Mermaid 코드 블록으로 다이어그램을 함께
   제공한다(마크다운 문서 내에서 렌더링 가능하도록 텍스트로 작성).
   - 상호작용/흐름: Sequence Diagram, Activity Diagram
   - 상태 기반 동작: State Machine Diagram
   - 액터-기능 관계: Use Case Diagram
   - 시스템 요구사항 구조/파생 관계: SysML Requirement Diagram
     (`requirement`, `deriveReqt`, `satisfy` 관계 표기)
   - 다이어그램은 요구사항 서술문과 반드시 내용이 일치해야 하며, 다이어그램
     이 요구사항 텍스트보다 더 많거나 다른 동작을 암시해서는 안 된다.

## 4. 비기능 요구사항 작성 규칙 (ISO/IEC 25010 기준)

- 비기능 요구사항은 ISO/IEC 25010의 8개 품질특성 분류를 참고하여
  분류한다: 기능적합성(Functional Suitability), 성능효율성(Performance
  Efficiency), 호환성(Compatibility), 사용성(Usability), 신뢰성
  (Reliability), 보안성(Security), 유지보수성(Maintainability),
  이식성(Portability).
- 각 비기능 요구사항은 다음을 포함한다.
  1. **품질특성 분류**(위 8개 중 하나 이상)
  2. **서술문**: 정량적이고 측정 가능한 기준으로 작성한다. "충분히 빠르게",
     "안정적으로", "사용자가 만족할 만큼" 같은 모호하고 측정 불가능한
     표현을 금지한다.
  3. **검증 방안**: 실제로 수행 가능한 방법만 제시한다.
     - 허용: 특정 도구/장비로 측정 가능한 성능 테스트(예: "특정 조건에서
       응답시간을 오실로스코프/로깅 도구로 측정하여 목표값 이내인지 확인"),
       정적 분석, 코드 리뷰 체크리스트, 내구성/신뢰성 시험(고장주입,
       장시간 구동), 보안 취약점 스캔/침투테스트, 이식성 확인을 위한 다중
       플랫폼 빌드/실행 테스트 등 — 프로젝트가 실제로 보유했거나 확보
       가능한 도구/절차 기준으로 제안한다.
     - 금지: 검증 주체·방법·판정기준이 없는 방안("추후 확인", "사용자
       피드백으로 판단" 등 정량 기준 없는 방안), 현재 프로젝트 환경에서
       확보 불가능한 장비/도구를 전제로 한 방안(예: 존재 확인 없이
       특정 상용 계측 장비를 가정), 측정 불가능한 주관적 판단에만 의존하는
       방안.
     - 검증 방안이 실행 가능한지 확신할 수 없으면, 그렇게 표시하고
       사용자에게 실제 보유 장비/툴체인을 확인한다.

## 5. 명확성(Clarity) 확보 규칙

- 능동태, 현재형, "shall" 기반 단문을 사용한다.
- 모호 표현(가능한 한, 적절히, 충분히, 대체로, 필요시 등)을 사용하지 않는다.
  사용해야 한다면 정량적 기준으로 구체화한다.
- 대명사(이것, 그것 등)로 대상이 불명확해지는 문장을 피하고, 항상 명시적
  주어/목적어를 사용한다.
- 하나의 요구사항에는 "그리고/또한"으로 여러 요구를 묶지 않는다(원자성
  위반). 여러 요구가 있으면 별도 ID로 분리한다.
- 프로젝트 전용 용어는 용어집(Glossary)에 정의하고, 문서 전체에서 동일한
  용어만 사용한다(동의어 혼용 금지).

## 6. 일관성(Consistency) 확보 규칙

- 동일한 개념·신호·구성요소에는 문서 전체에서 동일한 이름을 사용한다.
- 상위 요구사항과 하위 요구사항 사이에 서로 모순되는 조건/수치가 없는지
  검토한다.
- 우선순위, ASIL 등급, 상태 값 등은 문서에서 정의한 값 집합 내에서만
  사용한다(임의의 새 값 생성 금지).
- 요구사항을 추가/수정할 때마다, 관련 기존 요구사항과 충돌 여부를 점검하고
  충돌이 있으면 이를 명시적으로 사용자에게 보고한다.

## 7. 양방향 추적성(Bidirectional Traceability) 방안

- 이 프로젝트에서는 추적성을 **추적 매트릭스 파일**로 관리한다.
  기본 위치: `docs/requirements/traceability-matrix.md`
  (템플릿이 다른 위치/형식을 지정하면 그것을 따른다.)
- 추적 매트릭스는 최소한 다음 방향의 링크를 표 형태로 유지한다.
  - 상위 요구사항(예: 이해관계자 요구/시스템 요구) → 하위 요구사항(SW 요구)
  - 요구사항 → 설계 산출물(아키텍처/상세설계 요소)
  - 요구사항 → 테스트 케이스(검증 방안이 실제로 구현된 테스트)
  - 요구사항 → 소스 코드 모듈(가능한 경우)
- 표의 각 행은 최소 컬럼: `요구사항 ID`, `상위 요구사항 ID`, `설계 산출물`,
  `테스트 케이스 ID`, `구현 모듈`, `상태`.
- **절차**: 새 요구사항을 추가하거나 기존 요구사항을 수정/삭제할 때마다
  같은 작업 안에서 추적 매트릭스를 함께 갱신한다. 하위 산출물(설계, 코드,
  테스트)이 아직 없으면 해당 컬럼을 "미정"으로 표기하고 나중에 채운다.
  추적 매트릭스 갱신을 요구사항 변경과 분리된 별도 작업으로 미루지 않는다.
- 요구사항 본문에도 관련 상위/하위 ID를 상호 참조로 기재하여(예: "상위:
  REQ-SYS-F-001", "파생: REQ-SW-F-003, REQ-SW-F-004"), 매트릭스 없이도
  단일 요구사항 문서 안에서 추적이 가능하게 한다.

## 8. 임시 산출물 구조 (정식 템플릿 도착 전)

```
# 요구사항 명세서 (임시 구조 — 정식 템플릿 적용 전)

## 1. 개요 / 범위 / 용어집

## 2. 기능 요구사항
### <ID> <제목>
- 우선순위 / 상태
- 서술문
- Input:
- Output:
- 다이어그램(PlantUML/Mermaid)
- 상위/파생 요구사항 참조

## 3. 비기능 요구사항
### <ID> <제목>
- 품질특성(ISO 25010):
- 서술문(정량 기준):
- 검증 방안(실행 가능):
- 상위/파생 요구사항 참조

## 4. ISO 26262 안전 요구사항 요약
- 관련 ASIL 등급, 근거 문서 참조

## 5. 추적성
- docs/requirements/traceability-matrix.md 참조
```

## 9. 하지 말아야 할 것

- 사용자가 아직 템플릿을 주지 않았는데 임의의 템플릿을 정식인 것처럼
  제시하는 것.
- ISO 26262/25010/A-SPICE 원문을 통째로 인용하는 것.
- 실행 불가능하거나 판정 기준이 없는 검증 방안을 제시하는 것.
- 요구사항 변경 후 추적 매트릭스 갱신을 누락하는 것.
- 모호한 표현을 검증 가능한 기준으로 구체화하지 않고 그대로 두는 것.
