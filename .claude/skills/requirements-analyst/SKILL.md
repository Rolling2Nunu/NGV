# 요구사항 분석가 (Requirements Analyst)

이 스킬은 자동차 임베디드 소프트웨어/시스템 프로젝트에서 ISO 26262와
A-SPICE PAM 4.1을 준수하는 요구사항 명세서를 작성하기 위한 절차와 규칙을
정의한다(A-SPICE SWE.1 담당).

**전제**: `aspice-common` 스킬(문서 스타일, 저작권 유의, 템플릿 사용
절차, TPL-TRC-001 스키마, 공통 금지사항)을 전제로 한다. 이 스킬은
요구사항 분석 고유 내용만 다룬다.

- `.claude/0_OEM_Sample/OEM-SWR-001_OEM SW 요구사항 사양서.docx` — 실제 작성 예시(OEM 입력 문서, 장 구성은 SWE.1 산출물과 다르지만 요구사항/인터페이스 표 서식 참고용)

## 1. 문서 구조 — TPL-SWE1-001 목차(확정)

1. 목적 및 적용범위(1.1 목적 1.2 적용범위 1.3 적용경계)
2. 요구사항 작성 및 판정 규칙(2.1 식별/상태 규칙 2.2 품질 판정 기준)
3. 상태와 우선순위
4. 기능 및 안전 관련 SW 요구사항(4.1 기능요구 4.2 안전관련 SW요구)
5. 입력 데이터 사전
6. 외부 인터페이스 요구
7. 비기능 및 환경 제약
8. 분석 결과와 가정
9. 하향 할당 및 검증 계획
10. 범위 밖 주장
11. 추적성
12. 참고자료

## 2. 요구사항 ID 및 분류 체계

- ID: 등록부/템플릿에 고정 서식 없음 — 이 스킬은 `REQ-SW-F-001`(기능),
  `REQ-SW-NF-001`(비기능) 형식 채택. 고유·불변.
- 분류 컬럼: OEM 샘플 실사례 방식 채택 — ASIL 등급 표기(예: "ASIL B 입력")
  또는 "QM". 안전 관련 시 ASIL(QM/A/B/C/D)과 근거(HARA/안전목표 등) 기재.
  근거 없으면 "ASIL 미정 — 근거 문서 필요".

## 3. 기능 요구사항 작성 규칙 (4장)

요구사항 표 컬럼(OEM 샘플 방식 + Input/Output 확장):

`ID | 분류(ASIL/QM) | 요구사항 | Input | Output | 수용기준 | 검증 수준`

- **요구사항**: "SW는 <조건>일 때 <행위>를 수행해야 한다" 능동태 단문,
  원자성(한 문장 한 요구).
- **Input/Output(자연어)**: 하위 설계서(SW 아키텍처/상세설계)가 그대로
  참고 가능하도록 이 표에 자연어로 선언. 예: `Input: 차속(km/h)`,
  `Output: 목표 가속도 명령(m/s^2)`. 물리량은 단위, 이산신호는 열거값
  명시. **동일 정보를 6장 "외부 인터페이스 요구" 표
  (`인터페이스ID/방향/주요데이터/단위·범위/오류처리`)에도 인터페이스
  단위로 반영**(요구사항-표 항목은 자연어 요약, 6장은 인터페이스 계약
  상세).
- **수용기준**: 정량적 판정 기준(검증 시 통과/실패 근거).
- **검증 수준**: PC/SIL/HIL/Web 등 실행 가능한 수준 표기.
- **다이어그램**: .drawio 사용(이 프로젝트 표준). TPL-SWE1-003
  스캐폴드(title/boundary/actor/element/edge)를 기반으로 실제 UML
  표기 셰이프로 채운다.
  - Use Case: 액터(`shape=umlActor`), 유스케이스(타원,
    `ellipse;whiteSpace=wrap;html=1;`), 시스템 경계(점선 사각형)
  - 상호작용/흐름: Sequence/Activity Diagram도 동일하게 drawio로 작성
    (라이프라인/화살표/스윔레인 셰이프 사용)
  - 상태 기반 동작: State Machine Diagram(drawio)
  - 다이어그램 내용은 요구사항 서술문과 반드시 일치.
- 요구사항마다 상위/파생 요구사항 ID를 상호 참조로 기재.

## 4. Use Case 명세 (필요 시, TPL-SWE1-002)

7장 구조: 1.목적/범위 2.액터와 시스템 경계 3.Use Case 목록(ID/명칭/목적/
주액터/관련요구사항/우선순위) 4.Use Case 상세(기본정보/사전조건·트리거/
기본흐름/대안흐름/예외흐름/사후조건) 5.비대상 시나리오 6.추적성
7.참고자료. 액터-기능 관계가 복잡한 기능 요구사항에 한해 작성.

## 5. 비기능 요구사항 작성 규칙 (7장, ISO/IEC 25010 기준)

- ISO/IEC 25010 8개 품질특성으로 분류: 기능적합성, 성능효율성, 호환성,
  사용성, 신뢰성, 보안성, 유지보수성, 이식성.
- 각 항목: 품질특성 분류 / 정량적 서술문(모호 표현 금지) / 검증 방안.
- **검증 방안은 실행 가능한 것만**: 허용 — 도구/장비로 측정 가능한 성능
  테스트, 정적분석, 리뷰 체크리스트, 신뢰성 시험(고장주입/장시간구동),
  보안 스캔/침투테스트, 다중 플랫폼 빌드/실행 테스트 등(보유·확보 가능
  전제). 금지 — 판정기준 없는 방안("추후 확인" 등), 확보 불가능한 장비
  전제, 주관적 판단 의존. 확신 없으면 "실행 가능 여부 확인 필요"로 표시.

## 6. 명확성(Clarity) 확보 규칙

- 능동태·현재형·"shall" 기반 단문.
- 모호 표현(가능한 한/적절히/충분히/대체로/필요시 등) 금지, 정량 기준으로
  구체화.
- 대명사로 대상 불명확해지는 문장 금지, 명시적 주어/목적어 사용.
- 원자성: "그리고/또한"으로 여러 요구 묶지 않음, 별도 ID로 분리.
- 프로젝트 전용 용어는 용어집(1장 또는 참고자료)에 정의, 동의어 혼용 금지.

## 7. 일관성(Consistency) 확보 규칙

- 동일 개념·신호·구성요소는 문서 전체에서 동일 이름 사용.
- 상위-하위 요구사항 간 모순 조건/수치 점검.
- 우선순위/ASIL/상태 값은 정의된 집합 내에서만 사용(임의 신규값 금지).
- 요구사항 추가/수정 시마다 기존 요구사항과 충돌 여부 점검, 충돌 발견 시
  사용자에게 보고.

## 8. 양방향 추적성 — TPL-TRC-001 컬럼 소유

- 이 스킬은 `Upper Req`, `SW Req` 컬럼을 채운다(스키마·경로·공통 절차는
  `aspice-common` 4장 참조).
- 요구사항 본문에도 상위/파생 ID를 상호 참조로 병기(매트릭스 없이도
  단일 문서 내 추적 가능하도록).

## 9. 하지 말아야 할 것 (이 스킬 고유 — 공통 금지사항은 `aspice-common` 7장 참조)

- 실행 불가능하거나 판정 기준이 없는 검증 방안을 제시하는 것.
- 모호한 표현을 검증 가능한 기준으로 구체화하지 않고 그대로 두는 것.
