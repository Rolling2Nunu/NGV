# TDD (Test-Driven Development)

## 문서 작성 스타일

단답형(개조식: 명사형 종결, 불필요한 서술어 생략).

## 0. 원칙 — Red-Green-Refactor

1. **Red**: 요구사항/상세설계 함수 계약(사전조건·사후조건·예외)을 근거로,
   아직 구현되지 않은 동작에 대한 테스트를 먼저 작성한다. 실행해서
   반드시 실패(Red)함을 확인한다.
2. **Green**: 해당 테스트를 통과시키는 **최소한의 구현**만 작성한다.
   과잉 구현(아직 요구되지 않은 기능) 금지.
3. **Refactor**: 테스트가 계속 통과하는 상태를 유지하며 구조를
   개선한다(중복 제거, 가독성, 품질 지표 충족). 리팩터링 중 동작 변경
   금지 — 동작이 바뀌면 그것은 리팩터링이 아니라 새 변경이므로 다시
   Red부터 시작한다.
4. 위 3단계를 함수/기능 단위로 반복한다. 구현을 먼저 작성하고 테스트를
   나중에 끼워 맞추는 순서는 TDD 위반.

## 1. 테스트 작성 규칙

- 한 테스트는 **하나의 동작(behavior)만** 검증한다.
- 테스트명은 의도를 드러낸다(예: `test_<함수>_<조건>_<기대결과>`).
- 구조는 Arrange(준비) → Act(실행) → Assert(검증) 3단계로 구성.
- 외부 의존성(파일/네트워크/시간/난수 등)은 목(mock)·스텁으로 격리해
  테스트를 결정적(deterministic)으로 만든다.
- 경계값·예외 경로도 반드시 테스트한다(정상 경로만 테스트하지 않는다).

## 2. 커버리지 매핑

- 상세설계 함수 계약(사전조건 위반 시 동작, 정상 경로, 경계값, 예외/오류
  처리)을 빠짐없이 테스트 케이스로 변환한다.
- 요구사항의 수용기준(requirements-analyst 산출물)과 테스트 결과가
  대응되는지 확인한다.

## 3. 프레임워크

- 이 프로젝트는 Python `unittest` 표준 사용(CLAUDE.md 지정). 테스트
  파일명은 `test_*.py`, 테스트 클래스는 `unittest.TestCase` 상속.

## 4. 하지 말아야 할 것

- 구현을 먼저 작성한 뒤 테스트를 끼워 맞추는 것.
- 테스트 없이 구현 코드만 커밋하는 것.
- 실패하는 테스트를 방치하거나 임의로 skip 처리하는 것.
- 한 테스트에 여러 동작을 검증해 실패 원인을 모호하게 만드는 것.
