# 진짜 테스트 작성 규칙 (Writing Good Tests)

출처: https://github.com/obra/superpowers `test-driven-development/writing-good-tests.md`
번역·각색(Python/unittest 기준).

**로드 시점**: 테스트를 작성/변경할 때, 모의객체(mock)를 추가할 때,
테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 "깨짐"을 잡기 위해 존재한다. 두 원칙이 전부를 지배한다.

```
1. 모든 테스트는 자신이 잡는 깨짐(break)의 이름을 댈 수 있어야 한다
2. 모든 테스트는 실제 대상을 실행해야 한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다 — 먼저 작성해 실제 코드를
대상으로 실패를 확인한 테스트는 이미 "실패할 수 있음"을 증명했고,
실제 의존성이 느리거나 외부적일 때만 모의객체를 쓸 자격을 얻는다.

## 원칙 1: 깨짐의 이름을 대라

테스트 본문을 쓰기 전에 답한다: **어떤 운영 코드 변경이 이 테스트를
실패시키는가 — 그 변경은 버그인가 설계 결정인가?** 잘못된 분기, 누락된
부작용, 잘못된 인자, 경계값, 깨진 계약을 잡을 때 테스트는 존재 가치를
갖는다.

**기대값은 독립적으로 도출한다.** 리터럴과 손으로 확인한 픽스처를
사용한다 — 테이블 기반 테스트에 리터럴 `want` 값을 쓰는 방식을 선호.
검사 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든
항상 통과한다.

```python
# X 거울 검증: 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery(tag="urgent")
assert buildSearchQuery(tag="urgent") == expected

# O 손으로 도출한 리터럴
assert buildSearchQuery(tag="urgent") == 'tag:"urgent"'
```

**변경 감지기(change detector) 금지.** 의도적 결정만 실패시킬 수 있는
테스트(상수 값, 정확한 메시지 문구, 내부 구조)는 재설계 때마다 울리고
버그에는 잠든다. 결정에 의존하는 동작을 테스트하라: `MAX_RETRIES == 5`가
아니라 "실패한 호출은 5번 재시도되고 6번째 시도는 없다".

**행위(behavior)를 테스트, 텍스트를 테스트하지 말 것.** 스크립트나
설정 파일이 특정 줄을 포함하는지 검사하는 것은 "소스가 소스다"만
증명한다. 스크립트는 통제된 입력으로 실행해 출력/부작용/종료코드를
검증한다.

**당신의 코드를, 프레임워크가 아니라.** 경계에서 당신의 코드가 맺는
계약(등록하는 라우트, 발행하는 쿼리, 만들어내는 페이로드)을 테스트한다.
업스트림(외부 라이브러리) 동작은 그쪽 유지보수자의 테스트 몫이다.

### 게이트(적용 전 확인)

```
테스트 본문 작성 전:
  이 테스트를 실패시킬 운영 코드 변경을 하나 특정한다.

  하나도 특정 못함        → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀜"     → 산출물을 실행해 효과를 검증
  의도적 결정만 잡음       → 변경 감지기임, 그 결정에 의존하는 동작을 테스트

  기대값이 검사 대상 코드 없이 도출됐는지 확인.
  IF 검사 대상 코드/헬퍼를 재사용했다면:
    리터럴 또는 손으로 확인한 픽스처로 교체
```

## 원칙 2: 실제 대상을 실행하라

**모의객체 자체를 검증하면 안 된다.** 모의객체가 있으면 통과, 없으면
실패하는 assert는 그 컴포넌트에 대해 아무것도 말하지 않는다. 실제
컴포넌트의 동작을 검증하라. 모의객체를 검증하고 있다면, 모킹을 풀거나
그 assert를 지운다.

```python
# O 실제 동작 검증
self.assertTrue(response.status_code == 200 and response.json()["ok"])

# X 모의객체 존재만 검증
self.assertTrue(mock_sidebar.called)
```

**적절한 수준에서 모킹한다.** 실제 메서드의 모든 부작용을 먼저 파악한
뒤, 느리거나 외부적인 동작만 대체하고 테스트가 의존하는 부분은 실제로
남긴다. 확신이 없으면 먼저 실제 구현으로 테스트를 돌려 무엇이 실제로
필요한지 관찰한다.

**더블(double)을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의
일부라면 그것을 검증한다 — 아무거나 받는 가짜는 아무것도 검증하지
않는다. 각 분기(성공/오류/형식오류)마다 별도 픽스처나 스파이를 둬서
엉뚱한 분기가 기대를 만족시키지 못하게 한다.

**모의 데이터는 실제 구조를 완전히 반영한다.** 테스트가 읽는 필드만이
아니라 실제 존재하는 모든 문서화된 필드를 모킹한다. 부분 모킹은 후속
코드가 누락된 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하는데
통합에서는 깨진다.

**운영 클래스에는 운영 메서드만.** 테스트만 필요로 하는 정리(cleanup)를
운영 클래스에 `destroy()`처럼 넣지 않는다. 테스트 유틸리티로 옮긴다.

**모킹이 복잡해지면 실제 컴포넌트를 우선한다.** 모의객체 설정이 테스트
로직보다 커지거나, 모의객체가 실제 컴포넌트의 메서드를 놓치거나, 모의
객체가 바뀔 때마다 테스트가 깨지면 실제 컴포넌트를 쓰는 통합 테스트로
전환한다.

### 게이트(적용 전 확인)

```
모의객체/테스트 헬퍼 추가 전:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 부분은 실제로
  유지 — 느리거나 외부적인 수준만 모킹.

  모의 응답은 실제 구조를 완전히 반영.

  테스트만 호출하는 메서드는 운영 클래스가 아니라 테스트 유틸리티에.

  모의객체 자체를 검증하려는 참인가?
    모킹을 풀거나 그 assert를 지운다.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩터링)이 "완료"의 정의다.
동작이 필요로 하는 테스트만 남긴다 — 사소한 코드와 사람이 읽는 설명
문서는 테스트가 필요 없고, 절차를 만족시키기 위해 쓴 테스트는 계속
유지보수 비용만 남긴다.

## 뮤테이션 점검

끝내기 전에 운영 코드를 마음속으로 다음처럼 바꿔보고, 현실적인 변형마다
최소 하나의 테스트가 실패해야 한다.

- 잘못된 상수/인자
- 잘못된 분기 처리
- 상태변경/부작용 누락
- 빈 값 또는 기본값 반환
- 0/빈값/None/미인가/형식오류 입력에 대한 검증 누락

아무 테스트도 잡아내지 못하는 변형이 있다면, 그 동작은 무방비 상태이거나
그 테스트가 동어반복이라는 뜻이다.

## 빠른 참고

| 상황 | 행동 |
|---|---|
| 아무 테스트나 작성할 때 | 잡아내는 깨짐을 이름 붙인다 — 버그지 결정이 아니게 |
| 기대값을 만들 때 | 손으로 도출, 검사 대상 코드로 계산 금지 |
| 스크립트/문서를 테스트할 때 | 실행/소비자 관점 검증, 텍스트 grep 금지 |
| 의존성 테스트에 손이 갈 때 | 당신 쪽 경계 계약을 테스트, 상대측 문서화된 메커니즘 아님 |
| 모킹된 요소를 검증하려 할 때 | 실제 컴포넌트를 테스트하거나 모킹을 해제 |
| 메서드를 모킹하려 할 때 | 부작용을 먼저 파악, 느리거나 외부적인 수준만 모킹 |
| 모의 응답을 만들 때 | 실제 구조를 완전히 반영 |
| 테스트 전용 정리가 필요할 때 | 테스트 유틸리티에 둔다 |
| 모의객체 설정이 커질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환 |
| 테스트 파일을 끝낼 때 | 뮤테이션 점검 실행 |

## 경고 신호

- 준비(setup)와 검증(assert)이 같은 객체를 공유해 항상 같음을 보장
- 패닉/크래시/셀렉터 누락으로만 실패할 수 있는 테스트
- 의도적 변경마다 실패하고 실수로 인한 깨짐에는 반응 안 함
- 기대값이 루프/빌더/헬퍼 뒤에 숨어 있음
- 소스 텍스트를 grep하거나 제거된 심볼이 계속 없는지만 확인
- 프레임워크만 남아도 여전히 의미 있는 테스트인가(아니면 무의미)
- 커버리지만을 위한 테스트, 부작용/결과를 확인하지 않음
- `*-mock` 테스트 ID를 검증, 모의객체를 제거하면 실패하는 assert
- 테스트 파일에서만 호출되는 메서드
- 모의객체 설정이 테스트의 절반 이상을 차지, 왜 필요한지 설명 못함
- "혹시 몰라서" 모킹
