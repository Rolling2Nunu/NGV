# 아키텍처 설계자 (Architecture Designer)

이 스킬은 A-SPICE PAM 4.1의 SYS.3(System Architectural Design) / SWE.2
(Software Architectural Design)와 ISO 26262 Part 6의 아키텍처 설계 원칙을
준수하는 아키텍처 설계서를 작성하기 위한 절차와 규칙을 정의한다.

## 문서 작성 스타일

단답형(개조식: 명사형 종결, 불필요한 서술어/수식어 생략). 예: "책임: 차속
필터링", "선정 사유: 결합도 최저". ID, 수치, 근거 등 필수 정보는 생략 금지.

## 0. 템플릿 — 확정, 실제 파일 사용

정식 양식 확정됨(교육용 저작권 표시 있으나 사용자 승인으로 무시하고 사용).
경로(저장소 루트 `D:\NGV\NGV` 기준):

- `.claude/0_WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx`
- `.claude/0_WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio`
- `.claude/0_WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`
- `.claude/0_WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx` — 산출물 ID 규칙(예: `ENG-SWE2-001`)

**산출물 생성 절차**: 마크다운 신규 작성 대신 위 docx/drawio 템플릿을
프로젝트 산출물 경로로 복사 후 `docx` 스킬 및 drawio XML 직접 작성으로
채운다. 파일명은 등록부 ID 규칙 따름(예: `ENG-SWE2-001_SW 아키텍처
설계서.docx`, `ENG-SWE2-002_SW 아키텍처 UML.drawio`).

## 1. 저작권 유의

A-SPICE PAM 4.1과 ISO 26262 **표준 원문**(조항 번호, 정확한 문구, 표
전문)은 VDA/intacs와 ISO 저작물 — 통째 인용 금지, 공개적으로 알려진 설계
원칙(SOLID, 응집도/결합도, 아키텍처 패턴 명칭)만 사용. (0_WP_Templates
구조 자체는 사용자 지시로 무시하고 사용.)

## 2. 문서 구조 — TPL-SWE2-001 목차(확정, 15장)

1. 목적 및 범위
2. 아키텍처 설계 원칙(분해, 결합도, 응집도, 인터페이스, 오류격리, 변경
   용이성) — **후보 아키텍처 비교/선정 결과는 이 장의 하위 절
   "2.x 후보 아키텍처 비교 및 선정"으로 삽입**(템플릿에 전용 장 없음)
3. 논리 아키텍처(3.1 요소: ID/명칭/목적/제공기능/소유책임, 3.2 관계와
   제약: 의존방향/호출관계/공유자원/금지결합)
4. 컴포넌트 책임(책임/입력/출력/상태/오류처리/할당요구사항)
5. 정적 의존성(순환의존 방지 기준)
6. 인터페이스 명세(6.1 내부: API/이벤트/데이터저장소/동기화, 6.2 외부:
   HW/통신/사용자/외부서비스)
7. 동적 동작(시퀀스/활동)
8. 상태 전이
9. 오류 격리와 안전 동작
10. 품질속성 분석
11. 통합 전략(통합단위/순서/인터페이스검증/스텁·드라이버/회귀범위) —
    **전략 수준만**. 상세 통합 순서표는 SWE.5 산출물(TPL-SWE5-001)
    담당 범위이나, 이 스킬 사용 시점에 SWE.5 스킬이 없으면 이 장에 상세
    순서표까지 포함해 작성(추후 SWE.5 전용 스킬 도입 시 이관 검토)
12. 요구사항 할당
13. 자원 및 배포 경계
14. 추적성
15. 참고자료

공통 골격(모든 TPL-*.docx 동일): 표지 → 문서통제(변경이력표, 작성검토
승인상태표) → 목차 → 본문.

## 3. 후보 아키텍처 제안 및 선정 절차 (필수, 순서 준수) — 2장에 기록

상세 설계 작성 **전** 반드시 순서 준수.

1. 요구사항(`requirements-analyst` 산출물/TPL-TRC-001 추적 매트릭스)과
   품질 속성 요구사항(성능/안전/이식성 등) 확인.
2. 맥락에 적합한 **2~4개 후보 아키텍처 구조** 제안: 계층형, 마이크로커널,
   이벤트기반/발행-구독, 서비스지향, 포트-어댑터(헥사고날), 파이프-필터,
   컴포넌트 기반 등. 각 후보: 구조 개요(drawio 스케치 또는 텍스트) / 장단점
   / 응집도·결합도·변경유연성·ISO 26262(freedom from interference, ASIL
   분해) 관점 적합성.
3. **사용자 선정 전 상세 설계 진행 금지.** 제안 후 사용자 선택 대기.
4. 선정 구조로 문서 2장 하위 절에 비교표+선정 사유 기록 후 상세 설계 진행.

## 4. 응집도/결합도 및 변경 유연성 원칙 (필수)

- **높은 응집력**: 컴포넌트당 단일 책임. 무관 기능 혼재 금지.
- **낮은 결합도**: 의존은 인터페이스(추상화)로만. 구체 구현/내부
  자료구조 직접 의존 금지. 순환 의존 금지. 공유 가변 상태 최소화.
- **변경 유연성**: 변경 예상 부분(HW 종속, 외부 프로토콜, 정책 로직)은
  별도 계층/모듈 분리. 안정 계층이 변경 가능한 하위 세부에 직접 의존
  금지(의존성 역전). 확장 지점(플러그인/전략패턴) 명시.

## 5. SOLID 원칙 적용

- **SRP**: 컴포넌트 변경 이유는 하나.
- **OCP**: 확장 시 기존 컴포넌트 수정 없이 대응(상속/구성/인터페이스
  추가).
- **LSP**: 인터페이스 구현체는 정확성 훼손 없이 교체 가능.
- **ISP**: 목적별로 분리된 인터페이스, 뭉뚱그린 인터페이스 강제 금지.
- **DIP**: 상위 모듈은 하위 구체 구현이 아닌 추상화(인터페이스)에 의존.

## 6. 컴포넌트 인터페이스 정의 규칙 (필수, 6장) — TPL-SWE2-001 6.1/6.2 매핑

- **모든 컴포넌트는 명시적 인터페이스 보유, 컴포넌트 간 통신은 정의된
  인터페이스로만.** 내부 자료구조/비공개 상태 직접 참조 금지.
- 인터페이스 필드: 제공자/사용자 컴포넌트, 오퍼레이션·시그널명, 입력
  (자연어+타입/단위), 출력(자연어+타입/단위), 호출조건(사전/사후조건),
  시간제약(동기/비동기, 실시간 제약), 오류계약(오류코드/타임아웃/재시도).
  - 6.1 내부: 컴포넌트 간 API/이벤트/데이터저장소/동기화
  - 6.2 외부: HW/통신/사용자/외부서비스
- 다이어그램: PlantUML/Mermaid 대신 **.drawio**(TPL-SWE2-002 스캐폴드
  기반, 실제 UML/SysML 표기로 채움) — Component Diagram(제공/요구
  인터페이스), Block Definition/Internal Block Diagram(SysML 포트),
  Sequence Diagram(상호작용 시나리오).
- 요구사항의 Input/Output 선언(requirements-analyst 4장 표, 6장 인터페이스
  요구)과 이 장의 인터페이스 정의가 서로 대응되는지 확인.

## 7. 컴포넌트 통합 순서 정의 (필수, 11장)

- 의존 관계 그래프 근거로 통합 순서 정의. 원칙: 하위(의존 적음)부터
  상향식. 다른 순서(하향식/위험기반) 채택 시 근거 명시.
- 통합 순서표 컬럼: 단계번호/통합대상 컴포넌트/선행 필요 컴포넌트/검증
  인터페이스/통합테스트 관점(SWE.4/SWE.5 연계).
- 순환 의존 발견 시 통합 순서 정의 불가 — 사용자에게 즉시 보고, 구조
  조정 제안.

## 8. ISO 26262 관련 사항 (9장 연계)

ASIL 할당/분해, freedom from interference 조치는 근거 문서(HARA, 안전
요구사항 등) 있을 때만 기재. 근거 없으면 "근거 문서 필요".

## 9. 추적성 — TPL-TRC-001 기준(확정)

- `requirements-analyst`와 동일 파일 공유:
  `.claude/0_WP_Templates/Engineering/Traceability/TPL-TRC-001_...`
  복사본(예: `ENG-TRC-001_양방향 요구사항 추적 매트릭스.xlsx`).
- 이 스킬은 `Architecture`, `Detailed Design` 컬럼을 채운다(컴포넌트/
  인터페이스 ID 기재).
- 아키텍처 요소 추가/변경 시 같은 작업 안에서 매트릭스 함께 갱신.

## 10. 하지 말아야 할 것

- 후보 아키텍처를 제안하지 않고 곧바로 하나의 구조로 상세 설계 진행.
- 컴포넌트 간 통신을 인터페이스 없이(직접 내부 참조로) 정의.
- 순환 의존이 있는데도 통합 순서를 임의로 지어내는 것.
- A-SPICE/ISO 26262 **표준 원문**을 통째로 인용하는 것.
- 아키텍처 변경 후 추적 매트릭스(TPL-TRC-001 기반) 갱신 누락.
- 실제 템플릿 파일(docx/drawio) 대신 임의의 마크다운 구조로 산출물 대체.
